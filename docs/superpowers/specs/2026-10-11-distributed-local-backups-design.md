# Распределённые локальные резервные копии KRiT

Дата: 11.10.2026  
Статус: требования согласованы, готово к реализации по утверждённому плану

## Цель

Исключить постоянное хранение резервных копий на сервере и автоматически сохранять
проверенные копии PostgreSQL на каждом Windows-компьютере, где установлен
KRiTManagement и выполнен вход под активной учётной записью программы.

Рабочая PostgreSQL-база `krit_bot` остаётся на сервере: без неё серверная программа
и MAX-бот работать не могут. Запрет относится к постоянным серверным архивам
резервного копирования.

## Согласованные требования

- Автоматическое копирование работает для SuperAdmin, директора и администратора.
- Каждый компьютер создаёт собственный независимый локальный комплект.
- Проверка запускается после успешного входа в KRiTManagement.
- На одном компьютере копирование выполняется не чаще одного раза за 24 часа.
- Локальное хранилище: подпапка `Backups` строго рядом с установленной
  программой KRiTManagement.
- Используется ротация: 7 ежедневных и 4 еженедельные доверенные копии.
- Незавершённая или повреждённая загрузка не заменяет последнюю доверенную копию.
- Восстановление баз и решения по подозрительным комплектам доступны только
  SuperAdmin.
- GitHub, релиз и публикация установщика выполняются отдельно, только после
  завершения общей проверки проекта.

## Расположение локального хранилища

Программа использует только каталог `Backups` рядом с самой программой:

- в собранной версии: `<каталог KRiTManagement.exe>\Backups`;
- при запуске из исходного проекта: `<каталог management\main.py>\Backups`.

Переноса или резервного сохранения в `%LOCALAPPDATA%`, документы пользователя и
другие системные каталоги нет. Установщик создаёт `Backups` отдельно и назначает
этому каталогу право записи для обычных пользователей Windows, не расширяя права
на исполняемые файлы программы. Обновление KRiTManagement сохраняет содержимое
`Backups` и никогда не включает этот каталог в заменяемый пакет файлов.

Если программа была скопирована вручную в каталог без права записи, резервирование
не перенаправляется незаметно в другое место: интерфейс показывает понятную ошибку
с точным путём и просьбой предоставить доступ к `Backups`.

## Архитектура экспорта без серверного архива

Сервер больше не создаёт постоянный `.backup` в `/var/lib/krit/backups`. Вместо
этого клиент запрашивает описание экспорта, затем скачивает дамп каждой разрешённой
базы непосредственно из стандартного вывода `pg_dump`.

### Серверные операции

1. Аутентифицированный клиент запрашивает манифест экспорта.
2. Сервер возвращает:
   - время формирования;
   - версию схемы;
   - разрешённый список баз;
   - контрольные счётчики критичных таблиц;
   - номер последней записи аудита.
3. Для каждой базы клиент открывает поток скачивания.
4. Сервер запускает `pg_dump --format=custom` с выводом в канал HTTP-ответа.
5. Дамп не записывается в постоянный файл на сервере.
6. Одновременно допускается ограниченное число экспортов, чтобы несколько
   компьютеров не перегружали PostgreSQL.

Доступ к экспорту получают только активные пользователи программы с завершённой
сменой первоначального пароля. Клиентские учётные записи клуба и пользователи MAX
к этому API доступа не получают.

### Локальные операции

1. KRiTManagement создаёт в каталоге `Backups` файл с суффиксом `.part`.
2. Поток дампа записывается локально с одновременным вычислением SHA-256.
3. После получения всех баз программа создаёт локальный контейнер `.backup` с
   манифестом, размерами и контрольными суммами.
4. Контейнер повторно открывается и проверяется.
5. Только после успешной проверки выполняется атомарное переименование готового
   файла и обновление `KRiT-latest-trusted.json`.
6. При обрыве сети `.part` удаляется, а предыдущая доверенная копия сохраняется.

Текущий формат локального контейнера сохраняется, чтобы существующий механизм
восстановления продолжил принимать ранее созданные копии.

## Запуск на каждом компьютере

Механизм фонового резервирования переносится из `AdministrationPage` в уровень
главного окна приложения, поэтому он создаётся для любой роли.

После успешного входа программа:

1. открывает локальное хранилище;
2. удаляет только незавершённые `.part`;
3. определяет последнюю доверенную копию;
4. ничего не скачивает, если ей меньше 24 часов;
5. иначе запускает один фоновый экспорт;
6. не блокирует интерфейс и не запускает второй экспорт параллельно.

Каждая установка получает случайный `installation_id`, сохранённый в локальных
настройках. Сервер хранит только журнал результата: идентификатор установки,
пользователя, время, размер и SHA-256. Содержимое базы в журнал не попадает. Это
позволяет SuperAdmin видеть, сколько компьютеров действительно получили актуальную
копию.

## Ротация и защита от потери данных

- После успешной установки новой доверенной копии запускается ротация старых
  комплектов.
- Доверенные копии: одна самая новая копия для каждого из 7 последних дней и
  одна самая новая копия для каждой из 4 предшествующих календарных недель.
- Более старые доверенные копии удаляются только после полной проверки и
  атомарной установки новой копии; неудачная загрузка ротацию не запускает.
- Последняя доверенная копия сохраняется всегда.
- Копия с необъяснимым уменьшением критичных данных получает статус
  `suspicious` и не заменяет указатель последней доверенной копии.
- Подозрительная копия не удаляется автоматической ротацией.
- Подтверждение или удаление подозрительной копии требует SuperAdmin.
- Нормальное удаление клиентов не считается аварийной потерей, если серверный
  журнал аудита продвинулся и подтверждает изменения.

## Восстановление

Восстановление остаётся в разделе «Администрирование» и доступно только SuperAdmin.
По умолчанию выбирается последняя доверенная локальная копия, но перед необратимой
операцией показываются её дата, размер, перечень баз и контрольная сумма.

Во время восстановления допускаются два временных исключения из запрета хранения:

- загруженный на сервер архив операции восстановления;
- страховочный комплект текущей рабочей базы.

Они необходимы для безопасного отката. Загруженный архив удаляется после завершения
операции. Страховочный комплект удаляется только после явного решения SuperAdmin,
как было согласовано ранее. Эти файлы не являются плановыми резервными копиями и
не используются для ежедневного хранения.

## Миграция существующего сервера

1. Выпустить совместимые изменения сервера и KRiTManagement.
2. Проверить создание новой потоковой копии на тестовом компьютере.
3. Проверить целостность уже существующих локальных копий.
4. Автоматический `BackupScheduler` на действующем тестовом сервере уже отключён,
   а каталог `/var/lib/krit/backups` вместе со старыми архивами удалён по прямому
   указанию владельца проекта.
5. Старый локальный каталог `%LOCALAPPDATA%\KRiT\Backups` вместе с тестовыми
   копиями также удалён. До реализации нового механизма доверенных локальных
   комплектов нет, что допустимо для ещё не выпущенного проекта.
6. После внедрения проверить, что серверный каталог не создаётся повторно и ни
   один маршрут больше от него не зависит.

## Изменения интерфейса

### Администрирование

Внутри раздела создаются вкладки:

- «Управление» — краткие карточки состояния, пользователи, управление службами,
  локальные копии и восстановление;
- «Информация о сервере» — подробное дерево показателей на всю высоту страницы без
  ограничения 235 пикселями.

Автоматическое обновление показателей продолжает работать только при открытом
разделе «Администрирование».

### Диалоги

При явном открытии другого диалога история прокручивается к последнему сообщению
после завершения перерасчёта документа Qt. После отправки собственного сообщения
чат также прокручивается вниз. Фоновое обновление текущего диалога сохраняет
позицию, если пользователь читает старые сообщения, и следует за новыми сообщениями
только когда пользователь уже находился внизу.

## Ошибки и наблюдаемость

- Ошибка локального копирования показывается ненавязчивым уведомлением и пишется в
  журнал; рабочая программа продолжает работать.
- Повтор выполняется при следующем запуске или вручную SuperAdmin.
- Сервер журналирует начало, успешное завершение и обрыв потока без содержимого
  базы и без секретов.
- В подробной информации отображаются дата последнего успешного экспорта и число
  установок с актуальной локальной копией.

## Проверки

- Регрессионные тесты потокового экспорта без создания серверного `.backup`.
- Проверка прав всех трёх ролей и запрета для неавторизованных пользователей.
- Обрыв потока, повреждённый дамп, неверная контрольная сумма и повторный запуск.
- Независимая ротация в каталогах `Backups` двух установок программы.
- Проверка, что `%LOCALAPPDATA%` и другие внешние каталоги не используются.
- Проверка сохранения `Backups` установщиком и обновлением программы.
- Сохранение последней доверенной копии при подозрительном уменьшении данных.
- Полный цикл восстановления из локального контейнера с проверкой страховочного
  комплекта и отката.
- UI-тест отдельной вкладки информации о сервере.
- UI-тест прокрутки нового диалога вниз после отложенной перерисовки и сохранения
  позиции при фоновом обновлении.

## Критерии готовности

- После штатного резервирования в `/var/lib/krit/backups` нет архивов баз.
- На каждом компьютере, выполнившем вход и остававшемся онлайн до окончания
  операции, появляется проверенная копия в `Backups` рядом с программой.
- После успешной новой копии старые доверенные комплекты удаляются строго по
  интервалам 7 ежедневных и 4 еженедельных копий.
- Поломка одного компьютера не мешает восстановлению с другого.
- Существующие локальные копии остаются совместимыми.
- Восстановление возможно только с подтверждением SuperAdmin и сохраняет путь
  безопасного отката.
