# Администрирование пользователей и перезапуск КРиТ

Дата: 04.10.2026

## Цель

Добавить в настольную программу разделы «Отчёты» и «Администрирование» с
ролевым доступом. Администрирование позволяет полностью управлять учётными
записями сотрудников и безопасно перезапускать отдельно MAX-бота или всю
серверную программу КРиТ без перезагрузки операционной системы.

## Роли и доступ

В системе существуют три роли сотрудников:

- `superadmin` — полный доступ, включая раздел «Администрирование»;
- `director` — доступ к разделам «Клиенты», «Учебный процесс» и «Рассылки»;
- `administrator` — доступ к тем же разделам, что и директор.

На первом этапе директор и администратор не различаются по правам. Сервер всё
равно хранит эти роли раздельно, чтобы позднее ограничения можно было добавить
без изменения формата учётных записей.

Матрица доступа:

| Раздел | SuperAdmin | Директор | Администратор |
| --- | --- | --- | --- |
| Клиенты | да | да | да |
| Учебный процесс | да | да | да |
| Рассылки | да | да | да |
| Отчёты | да | да | нет |
| Администрирование | да | нет | нет |

Недоступные ссылки скрываются в интерфейсе. Это только удобство интерфейса:
каждый административный API дополнительно проверяет роль на сервере и отвечает
`403`, если роль не `superadmin`. Будущие API отчётов должны принимать только
`superadmin` и `director`.

## Начальные учётные записи

При первом запуске нового production-сервера, когда таблица `admin_users`
пуста, автоматически создаётся защищённая запись:

- логин `Choose_Goose`;
- роль `superadmin`;
- временный пароль `123`;
- признак обязательной смены пароля.

Значение `123` является публичным одноразовым bootstrap-паролем и хранится в
исходном коде. Оно допустимо только потому, что сервер до его смены блокирует
все прикладные API для этой учётной записи. После успешной смены в БД остаётся
только хеш нового пароля, а `123` больше не действует. Повторные запуски не
пересоздают пользователя и не сбрасывают его пароль.

После входа с временным паролем настольная программа немедленно требует новый
пароль и его повтор. Закрытие этого окна отменяет вход. До успешной смены токен
можно использовать только для endpoint первоначальной смены пароля.

Защищённую запись `Choose_Goose` нельзя удалить, отключить или понизить. В
локальной SQLite-среде для разработки и автотестов вместо production-bootstrap
сохраняется `admin/admin` с ролью `SuperAdmin`.

## Модель данных и миграция

Таблица `admin_users` расширяется полями:

- `full_name` — ФИО сотрудника, обязательная строка;
- `role` — одно из `superadmin`, `director`, `administrator`;
- `must_change_password` — блокировка прикладного доступа до первой смены;
- `protected_account` — запрет удаления, отключения и понижения системной
  учётной записи;
- существующее поле `active` продолжает определять возможность входа.

Миграция:

1. добавляет новые поля с безопасными временными значениями;
2. назначает существующей записи `admin` роль `superadmin`;
3. назначает остальным существующим записям роль `administrator`;
4. отмечает существующий `admin` как обычную, незащищённую тестовую запись;
5. делает поля обязательными и добавляет ограничение допустимых ролей;
6. обновляет ожидаемую Alembic-ревизию сервера.

SQLite-тесты получают ту же итоговую схему через SQLAlchemy metadata.

## Авторизация

Ответ `POST /api/v1/auth/login` дополнительно содержит профиль вошедшего
пользователя: `id`, `full_name`, `username`, `role`, `must_change_password`.
JWT остаётся короткоживущим и содержит идентификатор пользователя; актуальная
роль и признак обязательной смены проверяются по БД при каждом защищённом
запросе. Поэтому изменение или отключение учётной записи начинает действовать
без ожидания окончания токена.

`POST /api/v1/auth/change-initial-password` принимает новый пароль только для
авторизованной записи с `must_change_password=true`. Операция заменяет хеш,
атомарно снимает признак и выдаёт обычный профиль сеанса. Все остальные
защищённые endpoints до этого отвечают `403` с отдельным машинно различимым
сообщением о необходимости смены пароля.

Настольный клиент сохраняет профиль только в памяти текущего сеанса. Он строит
навигацию после входа и добавляет раздел «Администрирование» только для
`superadmin`.

## API администрирования

Все маршруты находятся под `/api/v1/administration` и требуют `SuperAdmin`.

### Пользователи

- `GET /users` — список учётных записей без хешей и паролей;
- `POST /users` — создание пользователя по ФИО, роли, логину и паролю.
- `PATCH /users/{id}` — изменение ФИО, логина, роли и состояния доступа;
- `POST /users/{id}/password` — установка нового пароля;
- `POST /users/{id}/disable` — немедленное отключение доступа;
- `POST /users/{id}/enable` — восстановление доступа;
- `DELETE /users/{id}` — полное удаление учётной записи.

Границы ввода:

- ФИО: 3–250 символов после удаления внешних пробелов;
- логин: 3–100 символов, без пробелов, уникальный без учёта регистра;
- пароль: 7–256 символов, чтобы поддержать согласованный временный пароль;
- роль: только одно из трёх допустимых значений.

Дубликат логина возвращает `409`. Пароль никогда не включается в ответ и аудит.
Создание и каждое изменение пользователя записываются в
`learning_audit_events` с идентификатором инициатора, целевой учётной записью и
изменёнными несекретными полями.

Защитные ограничения:

- нельзя отключить или удалить собственную текущую учётную запись;
- нельзя отключить, удалить или понизить роль последнего активного
  `SuperAdmin`;
- нельзя отключить, удалить или понизить защищённую запись `Choose_Goose`;
- смена пароля выполняется отдельно и не возвращает пароль после сохранения;
- удаление требует отдельного подтверждения с ФИО и логином;
- при полном удалении ссылки из исторического аудита получают `NULL`, а сами
  события аудита и бизнес-история сохраняются.

## Перезапуск MAX-бота

`POST /api/v1/administration/restart-bot` последовательно:

1. блокирует одновременный повторный перезапуск;
2. останавливает текущую polling-задачу или повторно проверяет webhook;
3. запускает новую polling-задачу при polling-режиме;
4. возвращает результат и записывает аудит.

API и остальные фоновые задачи остаются доступны. Повторный запрос во время
операции возвращает `409`.

## Перезапуск серверной программы КРиТ

`POST /api/v1/administration/restart-server` не перезагружает ОС. Маршрут:

1. проверяет роль `SuperAdmin`;
2. записывает и фиксирует событие аудита;
3. отвечает, что перезапуск принят;
4. с небольшой задержкой корректно завершает процесс КРиТ.

Production-служба systemd должна иметь `Restart=always` и подходящий
`RestartSec`, поэтому после завершения процесс автоматически поднимается снова.
API не принимает имён сервисов, команд или аргументов от клиента и не запускает
shell. В тестах завершение процесса заменяется внедрённым callback, чтобы
проверить поведение без остановки тестового процесса.

После нажатия настольная программа показывает состояние «Сервер
перезапускается…» и периодически обращается к `/health`. Когда health-check и
повторная авторизация успешны, интерфейс сообщает о восстановлении соединения.
Если восстановление не произошло за ограниченное время, пользователь получает
понятное сообщение и может войти повторно вручную.

## Резервное копирование

KRiTManagement сохраняет на локальном компьютере актуальную полную резервную
копию всех баз данных, принадлежащих КРиТ. Чужие базы данных, размещённые на том
же PostgreSQL-сервере, в архив не включаются.

Копирование выполняется:

- один раз после успешного запуска и входа в KRiTManagement;
- затем не чаще одного раза за 24 часа, если программа непрерывно работает;
- вручную по кнопке «Создать резервную копию сейчас».

Копирование при закрытии программы и отдельный процесс-наблюдатель не
используются. Это исключает дополнительный дамп при каждом коротком сеансе и не
создаёт ложной гарантии получения данных с уже недоступного сервера.

Полный дамп содержит персональные данные и хеши учётных записей, поэтому его
получение доступно только `SuperAdmin`. Автоматическое копирование запускается
только в сеансе SuperAdmin. Остальные роли не видят содержимое архива и не
могут вызвать backup API.

### Серверная часть

`POST /api/v1/administration/backups` создаёт согласованный PostgreSQL-дамп в
custom-формате через фиксированный, не зависящий от входных данных вызов
`pg_dump`. Имена команд, баз и файлов не принимаются от клиента. Одновременно
разрешена только одна операция; повторный запрос получает `409`.

`GET /api/v1/administration/backups/{id}` передаёт готовый архив по HTTPS вместе
с размером и SHA-256. Временные серверные файлы имеют ограниченный срок жизни и
удаляются после скачивания либо по фоновой очистке. Пароли БД не попадают в
командную строку, ответы API или журналы.

Для локальной SQLite-среды тестовый backend формирует согласованную копию через
SQLite backup API, поэтому тот же клиентский сценарий проверяется без
PostgreSQL.

### Локальное хранение

Архив хранится в каталоге данных пользователя Windows:
`%LOCALAPPDATA%\KRiT\Backups`. Основной файл имеет стабильное имя с датой и
версией схемы в метаданных.

Новая копия сначала загружается во временный файл `.part`. KRiTManagement
проверяет размер и SHA-256, затем атомарно переименовывает файл. Предыдущая
проверенная копия удаляется только после успешной замены. При сетевой, серверной
или дисковой ошибке временный файл удаляется, а предыдущая рабочая копия
обязательно сохраняется. Таким образом, локально хранится одна последняя
проверенная копия.

В «Администрировании» показываются дата, размер, версия схемы и состояние
последней локальной копии, а также кнопка ручного запуска. Фоновая операция не
блокирует основной интерфейс и сообщает об ошибке без удаления старого файла.

### Восстановление после потери сервера

Основной сценарий восстановления выполняется непосредственно из KRiTManagement.
SuperAdmin нажимает «Восстановить базы на новом сервере», а программа сама
использует последнюю проверенную резервную копию из стандартного каталога
`%LOCALAPPDATA%\KRiT\Backups`. Выбор файла пользователем не предусмотрен.
SuperAdmin указывает только:

- адрес нового сервера по HTTPS;
- порт, если используется нестандартный;
- логин SuperAdmin;
- пароль SuperAdmin на новом сервере.

Для только что развёрнутого сервера допускается первый вход `Choose_Goose` с
временным паролем `123`. Перед загрузкой архива KRiTManagement требует заменить
временный пароль. Введённый пароль используется только в памяти на время
операции, не сохраняется в настройках и не попадает в журналы.

Клиент сначала проверяет `/health`, TLS-соединение и полномочия SuperAdmin,
затем потоково передаёт архив по HTTPS. Прямое подключение настольной программы
к PostgreSQL, а также ввод пароля Linux, SSH или PostgreSQL не требуются.

Перед отправкой KRiTManagement читает `KRiT-latest.json`, проверяет наличие,
размер и SHA-256 файла `KRiT-latest.backup`. Если последней проверенной копии
нет, восстановление не начинается и интерфейс предлагает сначала создать
резервную копию.

Сервер проверяет размер, SHA-256, custom-формат `pg_dump` и совместимость версии
схемы. Автоматическое восстановление разрешено только на новом сервере, где
таблицы отсутствуют либо содержат исключительно созданные установщиком пустые
заглушки и первоначальную учётную запись `Choose_Goose`. Если обнаружены
клиенты, занятия, сообщения или другие рабочие данные, сервер отклоняет запрос
с `409` и ничего не изменяет. Таким образом, обычная кнопка восстановления не
может случайно перезаписать действующую базу.

Для запуска операции пользователь подтверждает замену пустых баз-заглушек.
После этого серверный помощник:

1. переводит КРиТ в режим обслуживания;
2. останавливает рабочий процесс и MAX-бота;
3. восстанавливает только базу `krit_bot` через `pg_restore`;
4. применяет миграции установленной версии;
5. запускает серверную программу КРиТ и MAX-бота;
6. публикует состояние операции для KRiTManagement.

KRiTManagement показывает ход загрузки и восстановления, ожидает успешный
`/health`, принудительно завершает старый сеанс и предлагает войти заново. После
восстановления защищённая запись `Choose_Goose` гарантированно остаётся активным
SuperAdmin. Ей назначается временный пароль `123` и признак обязательной смены,
чтобы пароль из старой базы не заблокировал доступ на новом сервере. Все ранее
выданные токены становятся недействительными.

Загрузка выполняется как отдельная операция с идентификатором:

- `POST /api/v1/administration/restores` — создать операцию и передать
  метаданные архива;
- `PUT /api/v1/administration/restores/{id}/content` — потоково загрузить
  содержимое;
- `POST /api/v1/administration/restores/{id}/apply` — подтвердить замену базы;
- `GET /api/v1/administration/restores/{id}` — получить состояние и результат.

Одновременно допускается только одна операция backup или restore. Сервер
принимает файлы только в фиксированный закрытый каталог, не использует
переданные клиентом пути или команды и удаляет незавершённые загрузки по сроку
жизни. Состояние восстановления хранится вне заменяемой базы, чтобы его можно
было прочитать после перезапуска службы.

Точные локальные и серверные каталоги, назначение файлов и последовательность
автоматического и аварийного ручного восстановления перечислены в корневом
файле `RESTORE_DATABASES.txt`. Файл включается в исходный репозиторий и
Windows-пакет поставки.

## Интерфейс

После «Рассылок» добавляются пункты «Отчёты» и «Администрирование» в указанном
порядке.

«Отчёты» на первом этапе содержит заголовок и оформленную заглушку «Раздел
находится в разработке». Раздел видят только `SuperAdmin` и директор.

Страница «Администрирование» содержит:

1. таблицу пользователей: ФИО, логин, роль, состояние;
2. кнопку «Добавить пользователя» и модальное окно с полями ФИО, роль, логин,
   пароль и повтор пароля;
3. действия выбранной записи: «Изменить», «Сменить пароль», «Отключить доступ»
   или «Включить доступ», «Удалить»;
4. блок «Управление сервисами»;
5. кнопку «Перезапустить MAX-бота»;
6. опасную кнопку «Перезапустить сервер КРиТ»;
7. блок «Резервные копии» с состоянием последнего архива и кнопкой ручного
   копирования;
8. кнопку «Восстановить базы на новом сервере», открывающую форму адреса,
   порта, логина и пароля. Под формой показываются дата и размер автоматически
   выбранной последней проверенной локальной копии.

Для обеих операций требуется подтверждение. Диалог серверного перезапуска явно
предупреждает о кратковременной недоступности всей программы. Кнопки блокируются
на время запроса, чтобы исключить повторные клики.

## Обработка ошибок

- `401` — сеанс недействителен;
- `403` — пользователь не является SuperAdmin;
- `409` — логин уже существует или перезапуск уже выполняется;
- `422` — некорректные поля формы;
- `423` — сервер временно находится в режиме обслуживания;
- `503` — механизм перезапуска недоступен в текущем окружении.

Внешнему клиенту не возвращаются трассировки, команды ОС, хеши паролей и детали
серверной конфигурации.

## Проверки

Backend-тесты должны доказать:

- миграция сохраняет существующего `admin` и назначает ему `superadmin`;
- пустая production-БД получает `Choose_Goose/123` только один раз;
- временная учётная запись не может обращаться к прикладным API до смены
  пароля;
- после смены новый пароль работает, `123` не работает и повторный запуск не
  сбрасывает пароль;
- директор и администратор получают `403` на каждом административном маршруте;
- SuperAdmin видит список и создаёт пользователя каждой роли;
- логин уникален без учёта регистра;
- пароль сохранён как хеш и отсутствует в API/аудите;
- отключённый пользователь не проходит авторизацию;
- SuperAdmin может изменить профиль и пароль другого пользователя;
- собственную запись и последнего активного SuperAdmin нельзя отключить,
  удалить или понизить;
- удаление учётной записи сохраняет аудит и бизнес-историю;
- бот перезапускается без остановки API;
- серверный callback вызывается только после успешной проверки роли и фиксации
  аудита;
- backup API недоступен директору и администратору;
- PostgreSQL-команда не строится из клиентского ввода и не раскрывает пароль;
- конкурентный запуск копирования получает `409`;
- архив сопровождается корректными размером, SHA-256 и версией схемы;
- restore API недоступен директору и администратору;
- некорректные адрес, пароль, контрольная сумма и формат архива отклоняются до
  изменения базы;
- серверный помощник получает только фиксированные пути и не строит команды из
  клиентского ввода;
- сервер с рабочими данными отклоняет автоматическое восстановление без
  изменения базы;
- пустые базы-заглушки нового сервера корректно заменяются данными из архива;
- ошибка `pg_restore` оставляет диагностируемое состояние и допускает повтор
  восстановления на новом сервере;
- после успешного восстановления старые токены недействительны, а
  `Choose_Goose/123` требует немедленной смены пароля.

UI-тесты должны доказать:

- раздел виден только SuperAdmin;
- вход с первоначальным паролем показывает обязательную форму смены до
  создания главного окна;
- «Отчёты» видят SuperAdmin и директор, но не администратор;
- заглушка отчётов отображается без активных недоступных действий;
- форма валидирует обязательные поля и совпадение паролей;
- список обновляется после создания, изменения, отключения, восстановления и
  удаления пользователя;
- обе команды требуют подтверждения;
- при серверном перезапуске отображается процесс восстановления соединения;
- автоматическая копия запускается после входа SuperAdmin и затем через 24 часа;
- успешная загрузка атомарно заменяет старую копию;
- ошибка загрузки или проверки сохраняет предыдущую копию;
- ручная кнопка запускает тот же проверенный сценарий;
- форма восстановления не содержит выбора файла, показывает автоматически
  найденную копию, не сохраняет пароль и очищает его после завершения;
- передача архива показывает прогресс и не блокирует интерфейс;
- восстановление невозможно без явного подтверждения;
- после перезапуска клиент ожидает `/health`, сбрасывает прежний сеанс и
  открывает форму входа.

Полная проверка перед выпуском: Ruff, все bot- и management-тесты, Alembic на
SQLite и PostgreSQL в CI, тест восстановления временной PostgreSQL-базы из
созданного дампа, проверка возврата страховочной копии при ошибке, сборка
Windows и smoke-запуск собранной программы.
