КРиТ — РАСПОЛОЖЕНИЕ РЕЗЕРВНЫХ КОПИЙ И ВОССТАНОВЛЕНИЕ
======================================================

Этот файл нужно хранить вместе с установщиком и локальной резервной копией.
Основной способ восстановления — кнопка в KRiTManagement. Ручные команды ниже
нужны как аварийный запасной вариант.


0. КАК РАЗВЕРНУТЬ НОВЫЙ СЕРВЕР — САМЫЙ ПРОСТОЙ ПУТЬ
---------------------------------------------------

Вам понадобятся: IP нового сервера, пароль root, домен, направленный на этот IP,
токен MAX-бота и файл KRiTServer.tar.gz.

1) Откройте Windows PowerShell и подключитесь (замените SERVER_IP):

   ssh root@SERVER_IP

   Например, `ssh root@178.217.99.218` означает пользователя root и IP сервера;
   это НЕ публичный адрес программы и НЕ надо вводить в KRiTManagement.

2) В другом окне PowerShell отправьте архив на сервер:

   scp KRiTServer.tar.gz root@SERVER_IP:/root/

3) Вернитесь в окно SSH и выполните по очереди:

   cd /root
   tar -xzf KRiTServer.tar.gz
   bash deploy/install-krit-server.sh

4) Установщик спросит только:
   - домен без `https://`, например `krit.example.ru`;
   - токен MAX-бота (при вводе он не отображается — это нормально).

5) Дождитесь строк «КРиТ установлен и запущен» и
   «Первый вход: Choose_Goose / 123».

6) Откройте KRiTManagement. Адрес программы имеет вид:
   https://ВАШ-ДОМЕН/krit-api/api/v1
   Первый логин: Choose_Goose, пароль: 123. Сразу задайте новый пароль.

7) Если нужно вернуть сохранённые данные, откройте «Администрирование» ->
   «Восстановить базы». Файл выбирать не надо: программа сама возьмёт последнюю
   доверенную копию из стандартной папки Windows.


1. ГДЕ KRiTManagement ХРАНИТ ПОСЛЕДНЮЮ КОПИЮ В WINDOWS
------------------------------------------------------

Каталог:
%LOCALAPPDATA%\KRiT\Backups

Файлы:
%LOCALAPPDATA%\KRiT\Backups\KRiT-ДАТА-ВРЕМЯ.backup
%LOCALAPPDATA%\KRiT\Backups\KRiT-ДАТА-ВРЕМЯ.json
%LOCALAPPDATA%\KRiT\Backups\KRiT-latest-trusted.json

Файл .backup — проверенный комплект всех баз КРиТ.
Одноимённый .json — дата, версии схем, размеры, SHA-256 и состав комплекта.
KRiT-latest-trusted.json — указатель на последнюю доверенную копию, которую
программа автоматически использует при восстановлении.

Хранятся 7 последних ежедневных и 4 последних недельных копии. Самые старые
удаляются только после успешной загрузки и проверки новой копии. Новый архив
сначала скачивается как временный файл .part — использовать его нельзя.

Если данные уменьшились после штатного удаления через КРиТ, программа сверяет
это с журналом действий и принимает копию. Если данные исчезли без записи в
журнале, копия получает состояние «Подозрительная» и не заменяет последнюю
доверенную. Проверить её можно в разделе «Администрирование».


2. АВТОМАТИЧЕСКОЕ ВОССТАНОВЛЕНИЕ БАЗ
------------------------------------

1) для нового сервера сначала установите и запустите серверную часть КРиТ; для
   старого сервера убедитесь, что его API отвечает;
2) в KRiTManagement откройте:
   Администрирование -> Резервные копии -> Восстановить базы;
3) укажите HTTPS-адрес целевого сервера и порт;
4) укажите логин и пароль SuperAdmin целевого сервера;
5) при первом входе используйте Choose_Goose и временный пароль 123, затем
   обязательно установите новый пароль по запросу программы;
6) проверьте показанные программой дату и размер последней локальной копии;
7) подтвердите восстановление. Для действующего сервера повторно введите пароль
   SuperAdmin и напечатайте слово ВОССТАНОВИТЬ;
8) дождитесь загрузки, проверки, восстановления, перезапуска сервера и бота;
9) войдите повторно, используя Choose_Goose и временный пароль 123, и сразу
   задайте новый постоянный пароль.

Выбирать файл не нужно: программа сама читает `KRiT-latest-trusted.json` и
берёт указанный проверенный комплект из `%LOCALAPPDATA%\KRiT\Backups`. Она
проверяет состав, размер и SHA-256 и передаёт архив по HTTPS. Восстановить можно как пустые базы нового
сервера, так и базы старого сервера после случайного удаления данных. Перед
заменой сервер всегда создаёт страховочную копию всего текущего комплекта. Затем
он полностью заменяет все базы КРиТ сохранёнными базами, применяет миграции и
перезапускает КРиТ. При ошибке хотя бы одной базы сервер возвращает весь прежний
комплект. Пароль хранится только в памяти на время операции. Пароль Linux, SSH
или PostgreSQL в KRiTManagement вводить не нужно.

После успешной проверки восстановленных данных откройте «Администрирование» и
найдите блок «Страховочная копия сервера». Сначала убедитесь, что клиенты,
занятия, сообщения и MAX-бот работают. Затем нажмите «Удалить страховочную
копию» и подтвердите действие. До решения SuperAdmin эта копия не удаляется, но
новое восстановление запустить нельзя. При обнаружении проблемы используйте
кнопку «Вернуть прежние базы».


3. РУЧНОЙ ПЕРЕНОС НА НОВЫЙ LINUX-СЕРВЕР
---------------------------------------

Временный закрытый каталог восстановления:
/var/lib/krit/restore

Файлы после переноса:
/var/lib/krit/restore/KRiT-latest.backup
/var/lib/krit/restore/KRiT-latest.json

Рекомендуемые права каталога: 0700.
Не помещайте резервные копии в каталог Nginx, /var/www или другой публичный
каталог.

Пример подготовки каталога:
sudo install -d -m 0700 /var/lib/krit/restore


4. РУЧНОЕ ВОССТАНОВЛЕНИЕ PRODUCTION POSTGRESQL
----------------------------------------------

Имя базы КРиТ:
krit_bot

База PostgreSQL не восстанавливается копированием файла в системный каталог.
Нельзя вручную заменять файлы в /var/lib/postgresql. Используйте pg_restore.

Перед восстановлением:
1) установите ту же или более новую совместимую версию PostgreSQL;
2) установите серверную программу КРиТ в /opt/krit-bot;
3) настройте закрытый файл окружения /etc/krit-bot/krit-bot.env;
4) задайте DATABASE_URL для базы krit_bot;
5) остановите службу КРиТ.

Команда остановки:
sudo systemctl stop krit-bot

Если роль PostgreSQL krit_bot ещё не существует, создайте её. Команда запросит
новый пароль интерактивно и не оставит его в истории терминала:

sudo -u postgres createuser --login --pwprompt krit_bot

На новом сервере, где рабочей базы ещё нет, создайте пустую базу:

sudo -u postgres createdb --owner=krit_bot krit_bot

Если неудачная попытка восстановления уже создала данные, удалите и заново
создайте ТОЛЬКО базу krit_bot. Не выполняйте эти команды на действующем сервере
без отдельной проверенной резервной копии:

sudo -u postgres dropdb --if-exists krit_bot
sudo -u postgres createdb --owner=krit_bot krit_bot

Файл `.backup` является комплектом. Сначала извлеките из него дамп PostgreSQL:

unzip -j /var/lib/krit/restore/KRiT-latest.backup krit_bot.dump \
  -d /var/lib/krit/restore

Затем восстановите дамп с немедленной остановкой при первой ошибке:

sudo -u postgres pg_restore --exit-on-error --clean --if-exists --no-owner \
  --role=krit_bot --dbname=krit_bot \
  /var/lib/krit/restore/krit_bot.dump

После восстановления примените миграции из установленной версии КРиТ:
sudo -u krit /opt/krit-bot/.venv/bin/krit-migrate

Запустите службу и проверьте её состояние:
sudo systemctl start krit-bot
sudo systemctl status krit-bot

Проверьте API локально на сервере:
curl --fail http://127.0.0.1:8080/health

Если имя systemd-службы или системного пользователя отличается, используйте
фактические значения нового сервера. Не вставляйте пароль PostgreSQL в команды
или этот файл.


5. ЛОКАЛЬНАЯ SQLITE-БАЗА ДЛЯ РАЗРАБОТКИ
---------------------------------------

Относительный путь в исходном проекте:
bot/data/krit.db

Типовой полный путь Windows:
D:\Рабочий стол\KRiT_Bot\bot\data\krit.db

Перед заменой SQLite-файла полностью остановите локальный backend КРиТ. Новый
файл сначала поместите рядом под временным именем, проверьте его и только затем
атомарно замените krit.db. Production-сервер должен использовать PostgreSQL, а
не этот SQLite-файл.


6. ЧТО НУЖНО ПРОВЕРИТЬ ПОСЛЕ ВОССТАНОВЛЕНИЯ
-------------------------------------------

1) /health возвращает status=ok;
2) вход Choose_Goose с временным паролем 123 требует немедленно задать новый
   постоянный пароль;
3) отображаются клиенты, занятия, журналы, рассылки и пользователи;
4) MAX-бот запущен и получает сообщения;
5) версия Alembic соответствует установленной версии сервера;
6) создана новая локальная резервная копия с восстановленного сервера.


ВАЖНО
------

Не удаляйте единственную локальную копию до полной проверки восстановленного
сервера. Файл базы содержит персональные данные и хеши паролей — не отправляйте
его через общедоступные чаты и не храните в публичном облаке.
