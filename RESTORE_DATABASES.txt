КРиТ — РАСПОЛОЖЕНИЕ РЕЗЕРВНЫХ КОПИЙ И ВОССТАНОВЛЕНИЕ
======================================================

Этот файл нужно хранить вместе с установщиком и локальной резервной копией.
Команды восстановления выполняются только на новом или остановленном сервере.


1. ГДЕ KRiTManagement ХРАНИТ ПОСЛЕДНЮЮ КОПИЮ В WINDOWS
------------------------------------------------------

Каталог:
%LOCALAPPDATA%\KRiT\Backups

Файлы:
%LOCALAPPDATA%\KRiT\Backups\KRiT-latest.backup
%LOCALAPPDATA%\KRiT\Backups\KRiT-latest.json

KRiT-latest.backup — проверенный архив базы данных.
KRiT-latest.json — дата создания, версия схемы, размер и SHA-256 архива.

Новый архив сначала скачивается как KRiT-latest.backup.part. Этот временный
файл нельзя использовать для восстановления. Предыдущая проверенная копия
удаляется только после полной загрузки и проверки нового архива.


2. КУДА ПЕРЕНЕСТИ КОПИЮ НА НОВОМ LINUX-СЕРВЕРЕ
----------------------------------------------

Временный закрытый каталог восстановления:
/var/lib/krit/restore

Файлы после переноса:
/var/lib/krit/restore/KRiT-latest.backup
/var/lib/krit/restore/KRiT-latest.json

Рекомендуемые права каталога: 0700.
Не помещайте резервные копии в каталог Nginx, /var/www или другой публичный
каталог.

Пример подготовки каталога:
sudo install -d -m 0700 /var/lib/krit/restore


3. PRODUCTION POSTGRESQL
------------------------

Имя базы КРиТ:
krit_bot

База PostgreSQL не восстанавливается копированием файла в системный каталог.
Нельзя вручную заменять файлы в /var/lib/postgresql. Используйте pg_restore.

Перед восстановлением:
1) установите ту же или более новую совместимую версию PostgreSQL;
2) установите серверную программу КРиТ в /opt/krit-bot;
3) настройте закрытый файл окружения /etc/krit-bot/krit-bot.env;
4) задайте DATABASE_URL для базы krit_bot;
5) остановите службу КРиТ.

Команда остановки:
sudo systemctl stop krit-bot

Если роль PostgreSQL krit_bot ещё не существует, создайте её. Команда запросит
новый пароль интерактивно и не оставит его в истории терминала:

sudo -u postgres createuser --login --pwprompt krit_bot

На новом сервере, где рабочей базы ещё нет, создайте пустую базу:

sudo -u postgres createdb --owner=krit_bot krit_bot

Если неудачная попытка восстановления уже создала данные, удалите и заново
создайте ТОЛЬКО базу krit_bot. Не выполняйте эти команды на действующем сервере
без отдельной проверенной резервной копии:

sudo -u postgres dropdb --if-exists krit_bot
sudo -u postgres createdb --owner=krit_bot krit_bot

Восстановите архив с немедленной остановкой при первой ошибке:

sudo -u postgres pg_restore --exit-on-error --clean --if-exists --no-owner \
  --role=krit_bot --dbname=krit_bot \
  /var/lib/krit/restore/KRiT-latest.backup

После восстановления примените миграции из установленной версии КРиТ:
sudo -u krit /opt/krit-bot/.venv/bin/krit-migrate

Запустите службу и проверьте её состояние:
sudo systemctl start krit-bot
sudo systemctl status krit-bot

Проверьте API локально на сервере:
curl --fail http://127.0.0.1:8080/health

Если имя systemd-службы или системного пользователя отличается, используйте
фактические значения нового сервера. Не вставляйте пароль PostgreSQL в команды
или этот файл.


4. ЛОКАЛЬНАЯ SQLITE-БАЗА ДЛЯ РАЗРАБОТКИ
---------------------------------------

Относительный путь в исходном проекте:
bot/data/krit.db

Типовой полный путь Windows:
D:\Рабочий стол\KRiT_Bot\bot\data\krit.db

Перед заменой SQLite-файла полностью остановите локальный backend КРиТ. Новый
файл сначала поместите рядом под временным именем, проверьте его и только затем
атомарно замените krit.db. Production-сервер должен использовать PostgreSQL, а
не этот SQLite-файл.


5. ЧТО НУЖНО ПРОВЕРИТЬ ПОСЛЕ ВОССТАНОВЛЕНИЯ
-------------------------------------------

1) /health возвращает status=ok;
2) вход Choose_Goose работает с уже установленным новым паролем;
3) отображаются клиенты, занятия, журналы, рассылки и пользователи;
4) MAX-бот запущен и получает сообщения;
5) версия Alembic соответствует установленной версии сервера;
6) создана новая локальная резервная копия с нового сервера.


ВАЖНО
------

Не удаляйте единственную локальную копию до полной проверки восстановленного
сервера. Файл базы содержит персональные данные и хеши паролей — не отправляйте
его через общедоступные чаты и не храните в публичном облаке.
